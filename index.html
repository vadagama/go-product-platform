Почему Go-first

Для корпоративных приложений, каталогов, документооборота, редакторов, административных систем и офлайн-клиентов наиболее важны проверяемая логика, низкая сложность и быстрый цикл изменений. Go обычно обеспечивает достаточную серверную производительность при компактной модели конкурентности и понятном коде. Общая реализация правил между Go Server и Wails существенно сокращает дублирование. Rust не исключается, но перестает быть обязательным компонентом каждого продукта.

Приоритеты: корректность → простота → проверяемость → производительность по бенчмаркам → минимизация новых зависимостей. Проект не получает микросервисы, CQRS, Kafka или GPU только потому, что их можно добавить.

Итоговая спецификация

Рекомендуемый базовый вариант v11: Серверная часть на Go (net/http + Connect-Go), Доменное ядро на чистом Go, PostgreSQL 18.7 (19.0 проверка концепции совместимости), React+TypeScript web, Wails 3 desktop, Protobuf+Buf, native macOS dev без Docker с Git worktrees, фоновые E2E, одна финальная проверка перед слиянием, VM Docker Compose minimal. Rauthy/RustFS/OpenBao опциональны или общие инфраструктурные сервисы, не обязательные контейнеры каждого продукта.

Mobile: Wails 3 только после готового end-to-end устройства; при недостигнутом SLA — SwiftUI/UIKit и Kotlin/Compose с теми же Connect/Protobuf контрактами. Обмен в реальном времени: WebSocket бинарный Protobuf только для двусторонних сценариев. Sync: Electric/PowerSync по PoC, а не как обещание автоматической двусторонней синхронизации. AI SDK/GPU: opt-in.

Надежный результат — не только успешная компиляция: платформа должна на чистой VM развернуться, пройти security+smoke, восстановить данные из backup, не потерять offline mutations и выпускать подписанные клиенты, совместимые с API.

Состояние решения: Go-first принят как приоритет. Нативные мобильные приложения — полноценная допустимая ветка, а не крайняя мера. Производительность, синхронизация и зрелость Wails Mobile валидируются на реальном продукте с заранее определенными приемочными тестами.

Go против Rust: ожидаемая производительность

Это архитектурный прогноз, а не benchmark. Сравнивать нужно на одинаковом продукте, данных, UI, версии ОС и профиле сборки. В типичных бизнес-приложениях основная задержка находится в SQL, сетевых вызовах, графическом рендеринге и количестве обновлений UI, а не в нескольких миллисекундах выполнения доменной функции.

Архитектурные границы и модули

Базовый стиль: прагматичный модульный монолит. Разработка по feature, а не по искусственным горизонтальным слоям. Операции и доменные инварианты живут в общих пакетах Go; приложения содержат только адаптеры под их платформу.

Слой Что содержит Чего не содержит
domain правила, значения, состояния, проверки HTTP, SQL, Wails, UI, SDK
application use cases, транзакционные границы как интерфейсы JSX, HTTP handlers
adapters/postgres SQL, pgx, миграции доменные правила в SQL-триггерах без ADR
adapters/sqlite локальные операции и миграции серверные RLS-политики
adapters/connect Protobuf mapping, перехватчики аутентификации обход бизнес-сервисов
adapters/wails JS→Go методы, platform permissions независимые бизнес-правила
apps/mobile-native Swift/Kotlin UI и platform API несанкционированная запись в серверную БД

Не требовать реализации Repository, Unit of Work, Factory и Adapter для каждой CRUD-функции. Trait/interface добавляется там, где есть настоящая изменяемая граница или тестовая подмена. Контракты и инварианты обязательны; количество абстракций минимально.

Модель доменного инварианта

Показать пример кодаGO
package resource

import "errors"

type Element struct {
    ID       string
    WidthMM  int
    XMM      int
}

type Container struct { WidthMM int }

var ErrOutOfBounds = errors.New("element outside container")

func ValidatePlacement(s Container, f Element) error {
    if f.WidthMM <= 0 || f.XMM < 0 || f.XMM+f.WidthMM > s.WidthMM {
        return ErrOutOfBounds
    }
    return nil
}

Та же функция вызывается из Connect API и Wails, а на мобильном клиенте — только если выбран Go-бэкенд внутри приложения или создан осознанный Go native binding. См. API и realtime и Платформы.

Главный стандарт v11: модульный Go-монолит без инфраструктурной избыточности

Нормативное решение. Базовое приложение запускает один Go-процесс, одну PostgreSQL и один Vite-сервер только во время разработки. Пользователи, прикладные права, аудит, аналитика, уведомления, поиск, флаги, фоновые задания и машины состояний — модули и библиотеки внутри Go-приложения. Общая корпоративная инфраструктура подключается через адаптер, но не запускается по отдельному экземпляру на каждый продукт.

Внутри монолита нет сетевого RPC между модулями. Connect работает с клиентами, а WebSocket обслуживает событийный канал. Плагины не должны владеть чужими таблицами напрямую.

Модуль ≠ плагин ≠ отдельный сервис

Подход Что означает Когда выбирать
Встроенный модуль Обычный Go-пакет с явными экспортируемыми функциями; собирается в один бинарник По умолчанию, основная бизнес-функциональность
Плагин времени компиляции Подключаемая при сборке реализация интерфейса, включение через конфигурацию или профиль сборки Несколько необязательных возможностей и адаптеров
Runtime plugin Отдельно загружаемый исполняемый модуль с политиками и жизненным циклом Когда реально нужен динамический marketplace / сторонний код
Отдельный сервис Собственный процесс, сетевой контракт, мониторинг и развертывание Независимый runtime, ресурсы, безопасность или жизненный цикл

Не использовать Go plugin / .so как основу общей системы расширений: переносимость и строгая совместимость компилятора/зависимостей усложняют build и поддержку. Для большинства задач компоновка через обычные пакеты Go и явный реестр надежнее и быстрее. Если в будущем появятся недоверенные сторонние расширения, рассматривать отдельный процесс или sandboxed Wasm (например, wazero) после анализа угроз; это не обязательный базовый вариант.

// Упрощённый compile-time registry. Плагины собираются вместе с программой.
// Инициализация явная; это не динамическая загрузка .so.
package platform

type Module interface {
    Name() string
    Start() error
    Stop() error
}

type Registry struct{ modules []Module }

func NewRegistry(modules ...Module) *Registry {
    return &Registry{modules: modules}
}

func (r *Registry) Start() error {
    for _, module := range r.modules {
        if err := module.Start(); err != nil { return err }
    }
    return nil
}

Улучшение для рабочая среда: передавать context.Context в lifecycle, останавливать в обратном порядке, не реализовывать общий Module там, где простая функция инициализации короче. Реестр — шаблон для расширяемой платформы, не обязательная обертка всех пакетов.

GPU, ML и производительность

GPU опционален. Бизнес CRUD, транзакции, SQL, большинство таблиц и простой UI работают на CPU. Для графических приложений GPU обычно полезен для PixiJS/Three.js рендеринга; для распознавания фото — Core ML / ONNX / ML серверная часть; для массовой независимой численной оценки кандидатов — выделенный compute engine при наличии измеренного выигрыша.

Go не обязан реализовывать GPU-ядро. Возможны: WebGL/WebGPU в клиентской части, отдельный Rust/Metal/CUDA/ONNX обработчик задач по API или платформенный native модуль. CPU резервный вариант, ограничение конкуренции с UI и замеры на реальных устройствах обязательны.

API: Protobuf + Buf + Connect/gRPC

Единый машинно-проверяемый контракт — .proto. Наличие контрактов важнее того, читает ли разработчик JSON вручную. Binary Protobuf — основной wire format, но формат не заменяет проверки авторизации, корректности бизнес-команд и наблюдаемость.

Задача Транспорт Почему
Web → Go Connect unary + Protobuf Браузер, типизированный RPC, нормальная HTTP-инфраструктура
Wails/Desktop → Go Connect + Protobuf Общие схемы; Go/native транспорт
Нативные Swift/Kotlin → Go Connect или gRPC по доступным SDK Выбор драйвера и платформенной поддержки
Go ↔︎ сервисы Connect/gRPC При появлении реальных межсервисных границ
Односторонние live-обновления Потоковая передача от сервера Connect / SSE Может обойтись без WebSocket

Фото, CAD, OBJ, большие файлы HTTPS + S3 presigned URL Не пересылать большие объекты через RPC

Важные уточнения: Connect-Go может обслуживать Connect, gRPC и gRPC-Web через общий handler. Поддержка бинарного Protobuf не означает, что все клиенты автоматически отправят бинарный формат: настройка транспорт и Content-Type проверяются в контрактных тестах. gRPC потоковая передача из браузера имеет транспортные ограничения; browser-bidi не проектировать как замену WebSocket без проверки. Для web учитывать CORS, preflight, TLS, корпоративные прокси и потоковая передача HTTP-ответа.

Рекомендованный protobuf-контракт

Показать пример кодаPROTO
syntax = "proto3";
package resource.v1;

option go_package = "example.com/product/gen/resource/v1;resourcev1";

import "google/protobuf/timestamp.proto";

service ResourceService {
  rpc GetResource(GetResourceRequest) returns (GetResourceResponse);
  rpc MoveElement(MoveElementRequest) returns (MoveElementResponse);
}

message GetResourceRequest { string resource_id = 1; }
message GetResourceResponse {
  string resource_id = 1;
  uint64 revision = 2;
  repeated Element elements = 3;
}
message Element { string id = 1; int32 x_mm = 2; int32 y_mm = 3; }
message MoveElementRequest {
  string resource_id = 1;
  string element_id = 2;
  int32 x_mm = 3;
  int32 y_mm = 4;
  uint64 expected_revision = 5;
  string idempotency_key = 6;
}
message MoveElementResponse {
  uint64 revision = 1;
  google.protobuf.Timestamp committed_at = 2;
}

Revision сравнивается атомарно внутри PostgreSQL-транзакции; idempotency_key предотвращает повторное применение одной команды. Типы идентификаторов на wire могут быть string, а в Go domain — строгие newtypes. Бизнес-валидация исполняется на сервере, даже если клиент уже проверил размещение.

Правила эволюции схем

Никогда не переиспользовать удаленные номера и имена полей (reserved), не изменять wire тип существующего поля без миграции, использовать новые поля с безопасными значениями по умолчанию, определять наличие значения через optional или message-wrappers, сохранять совместимость старых клиентов. Для частичных обновлений использовать явно определенный сообщение частичного обновления / FieldMask, а не неявный merge. Старый клиент и новый сервер должны сосуществовать в течение период поддержки выпуска. См. также правила совместимости.

Collaboration: события, ревизии и восстановление

WebSocket — транспорт, но не надёжный журнал событий. Команды записи идут через Connect; подтвержденные изменения публикуются после commit (транзакционная очередь исходящих событий). Сохраняемое событие имеет event_id, resource_id, revision, committed_at, payload. Клиент при reconnect запрашивает изменения с revision N либо актуальный snapshot; сервер определяет срок хранения replay-лога и поведение за его пределами.

Для курсоров и presence допустимы потери и coalescing; для MoveElement, Rename, Approve необходима надежная запись и подтверждение, обычно не по WebSocket-команде. Для конкурентных редакторов добавить sequencing, optimistic конкурентность, права на ресурс и явную стратегию конфликтов. CRDT/OT использовать лишь при реальной потребности совместного редактирования одного объекта и после отдельного ADR.

Показать пример кодаPROTO
syntax = "proto3";
package resource.v1;
message RealtimeEvent {
  string resource_id = 1;
  uint64 revision = 2;
  string event_id = 3;
  oneof payload {
    ElementMoved element_moved = 4;
    UserCursor user_cursor = 5;
  }
}
message ElementMoved { string element_id = 1; int32 x_mm = 2; int32 y_mm = 3; }
message UserCursor { string user_id = 1; int32 x_mm = 2; int32 y_mm = 3; }

Проверки: пропуск событий, reconnect на 60 минут, смена разрешений в открытом сокете, ограничение скорости курсора, 100 одновременно подключенных клиентов и утечка между арендаторами. События WebSocket также должны проходить авторизацию канала и валидацию длины кадра.

Обмен в реальном времени и совместная работа без отдельного сервера сообщений

Для двунаправленных событий использовать coder/websocket + бинарный Protobuf; для обычных request/response — Connect RPC. WebSocket доступен из одного HTTP-сервер Go рядом с обработчики Connect. Никаких Redis/NATS/Kafka ради одного экземпляра на VM не требуется.

WebSocket контракт: проверять authorization при установке соединения и каждой подписке, ограничивать максимальный размер сообщения, иметь ограниченную очередь отправки, ограничения частоты запросов, heartbeat/timeout, backpressure и чистое закрытие. Каждое устойчивое изменение содержит resource_id, revision, event_id; после reconnect клиент получает snapshot+delta с last_revision. Смена прав должна отзывать подписку. Нельзя хранить состояние совместного редактирования только в памяти сервера.

На нескольких API-репликах широковещательная рассылка в памяти перестаёт быть общим. В этот момент можно добавить Postgres LISTEN/NOTIFY как сигнал (не надёжное хранилище), либо независимый pub/sub — но журнал истины остаётся в PG. Если требуется сложная CRDT-совместная работа, её нужно вводить как отдельный стандарт после сравнения Yjs/Automerge, а не симулировать через произвольные WebSocket-сообщения.

// Иллюстрация обработчика: типы Request/Response генерируются Buf.
type ResourceServer struct {
    Service *application.ResourceService
}

func (s *ResourceServer) MoveElement(
    ctx context.Context,
    req *connect.Request[resourcev1.MoveElementRequest],
) (*connect.Response[resourcev1.MoveElementResponse], error) {
    principal, err := auth.FromContext(ctx)
    if err != nil { return nil, connect.NewError(connect.CodeUnauthenticated, err) }
    revision, err := s.Service.MoveElement(ctx, principal, req.Msg)
    if err != nil { return nil, mapDomainError(err) }
    return connect.NewResponse(&resourcev1.MoveElementResponse{Revision: revision}), nil
}

application.ResourceService, auth.FromContext и mapDomainError — проектные функции. В полноценной реализации proto DTO следует трансформировать в доменный command на границе адаптера; код приведен для понимания, не как готовый компилируемый сервис. Контракты описаны в API и realtime.

Безопасность: Rauthy, OpenBao, RustFS

Rauthy: OIDC, MFA/passkeys, идентичность; Go API валидирует issuer/audience/JWKS и исполняет авторизацию subject × action × resource × tenant. Для сложных объектных прав добавить OpenFGA/Casbin только если это реально требуется. Не доверять только UI-ролям.

RustFS: S3 совместимое object storage; Go API проверяет файл, размер, тип, владельца и выдает короткоживущий presigned URL с ограничением scope. Upload finalize подтверждает checksum и owner. Доступ к административным S3 ключам никогда не дается клиенту. Совместимость конкретного S3 SDK проверить интеграционными тестами.

OpenBao (опциональный общий сервис): KV, динамические credentials и policies; Рабочая среда использует mTLS/auth method, доступ по необходимости, audit и ротацию. На локальном Mac можно использовать секреты только для разработки с короткой жизнью; секреты рабочей среды никогда не копировать в worktrees. В VM доставлять секреты через шаблон OpenBao Agent в защищённые файлы или через прямое обращение к SDK там, где нужны динамические операции. Bootstrap/Unseal отдельно от бизнес Compose. Для начальная зашифрованная конфигурация подходит SOPS + age.

Mobile/desktop: access/refresh tokens — Keychain / Android Keystore / platform-secure storage; не хранить серверные master keys. Любой Wails bridge метод проверяет permissions. Внешний HTML открывать вне привилегированного WebView; при iframe проводить независимую security review.

Идентификация, сессии и авторизация без отдельного сервиса пользователей

Три разных уровня: (1) аутентификация устанавливает, кто вошёл; (2) локальная учетная модель хранит членство, роль и профиль; (3) прикладная авторизация разрешает конкретное действие над конкретным ресурсом.

  • Внешнюю учетку связывать с локальным пользователем через пару issuer + subject, а не email. Привязка к исходному IdP допускает смену адреса и несколько провайдеров.
  • При наличии корпоративного IdP не разворачивать собственный Rauthy/Keycloak на каждый продукт. Для Go-клиента выбирать go-oidc и golang.org/x/oauth2; API отдельно проверяет JWT audience, issuer, expiry и права бизнес-операции.
  • Для автономного продукта при оправданных требованиях — SCS и PostgreSQL с защищёнными cookie, CSRF и средствами предотвращения brute-force; создание собственного identity provider не становится дефолтом.
  • Для authorization — маленький модуль access.Authorize(ctx, actor, action, resourceScope); при настройке сложных ролей добавлять Casbin в процессе, а OpenFGA только при настоящем графе отношений.
  • Права необходимо проверять в поиске, списках, статистике, экспорте, файлах, RPC, websocket subscriptions и фоновых действиях. Флаг функции не заменяет authorization — см. флаги.

Секреты: минимальный профиль и общий OpenBao при необходимости

Минимальный профиль: в DEV — .env.local вне Git (только тестовые значения), в PROD на VM — root-owned файлы / Compose secrets, шифрованные в Git через SOPS+age и расшифрованные при deployment. Compose secrets монтируются в контейнер как файлы; исходный файл на VM всё равно надо защищать. Шифрованные пользовательские токены хранятся в PostgreSQL вместе с key_version, а ключ шифрования приходит извне этой БД.

Общий OpenBao предпочтителен там, где нужны политики, аудит чтения секретов, PKI, динамические PG credentials и отзыв. Он может существовать как общий сервис компании, но не входит в локальный dev loop и не требуется каждому продукту. Если OpenBao используется, секреты поставляются через agent/файл либо явный Rust/Go vault-compatible клиент; приложение отвечает за обновление/перечитывание и сбои доставки.

Надёжные фоновые задачи внутри монолита: River

Основной стек: River + pgx + PostgreSQL + Go обработчик задач. Один бинарник может запускаться как app serve, app worker или app all для маленького окружения. Базовые правила:

  1. Бизнес-состояние, аудит и InsertTx задания помещаются в одну PG-транзакцию. Это предотвращает ситуацию «данные записались, а намерение отправить уведомление потерялось». River transactional enqueueing.
  2. Воркеры имеют ограниченный параллелизм, контексты отмены, deadline, retry с jitter и устойчивые idempotency keys.
  3. Внешняя система может выполнить действие, после чего обработчик задач упадет до отметки об успехе: при повторе нужен dedupe/сверка. At-least-once, не exactly-once.
  4. Для нескольких API-инстансов и при перерастании ресурса выделяется app worker в отдельный процесс, оставляя общую кодовую базу.
  5. Отдельный outbox не нужен только ради передачи задач в River в той же транзакции; для публикации независимых интеграционных событий может потребоваться отдельный outbox.
  6. River Pro Workflows — платный дополнительный модуль для оркестрации графов задач и сигналов; не включать Pro-функции в базовый набор с открытым исходным кодом. River Pro.

Надёжная операция перехода

  1. Начать PG-транзакцию и загрузить запись по фактической области видимости пользователя.
  2. Проверить command_id (повтор) и право выполнить действие.
  3. Защитить состояние от гонки: SELECT … FOR UPDATE либо optimistic row_version.
  4. Проверить бизнес-guards, вычислить новый state через чистый FSM.
  5. Сохранить state, row_version + 1, запись state_transitions с actor/time/definition_version.
  6. При необходимости транзакционно поставить River job (уведомление, интеграция, deadline).
  7. COMMIT; внешние HTTP/SMTP/S3 эффекты выполнять после COMMIT в обработчик задач.
Показать пример кодаGO
// Типизированное ядро для простого FSM: без сети, SQL и таймеров.
package workflow

import "errors"

type State string
type Event string
const (
    Draft State = "draft"
    Review State = "in_review"
    Approved State = "approved"
    Active State = "active"
)
const (
    Submit Event = "submit"
    Approve Event = "approve"
    Activate Event = "activate"
)
var ErrInvalidTransition = errors.New("invalid transition")

func Next(current State, event Event, checksPassed bool) (State, error) {
    switch {
    case current == Draft && event == Submit:
        return Review, nil
    case current == Review && event == Approve && checksPassed:
        return Approved, nil
    case current == Approved && event == Activate:
        return Active, nil
    default:
        return "", ErrInvalidTransition
    }
}

Для сложной модели заменить логику switch на qmuntal/stateless, оставив ту же внешнюю транзакционную границу. Нельзя полагаться, что FireCtx автоматически откатывает SQL при ошибке callback: библиотека управляет in-memory состоянием, а не распределенными транзакциями.

Таймеры, ожидания и старые события

Критичный инвариант: запланированный таймер/ответ внешней системы содержит step_instance_id или round_version. Worker перед действием сравнивает текущий ID этапа, deadline и актуальность версии записи. Проверка одного state == in_review ошибочна: процесс мог вернуться в то же состояние уже во втором цикле.

Хранить entity_id, state, row_version, definition_version (если процессы долгие), step_instance_id, deadline_at. Таймеры River создаются по ScheduledAt, но не гарантируют выполнение ровно в назначенную секунду. Вызов cron или постоянно спящая goroutine не заменяют persisted timers.

Проверять: одновременные Approve/Reject, повтор команды, restart между COMMIT и внешним действием, поздний ответ старой попытки, долгий зависший этап, смена определения FSM. Для моделей состояния полезны тесты свойств и генерация диаграмм из кода, а не независимая диаграмма, которую агент забудет обновить.

Фоновые локальные E2E: без блокировки агента

Цель: агент продолжает менять код и получать unit-тесты, пока отдельный низкоприоритетный процесс запускает browser smoke по измененным маршрутам. Это локальная активная проверка, а не гарантия, что последний результат относится к последней незавершенной правке.

Два режима, решающие разные задачи

Режим Инструмент Триггер Зачем
Interactive visual Playwright test --ui и выборочный watch Агент активирует тест в UI Диагностика, trace/time travel, сравнение скриншотов
Background continuous watchexec + Playwright smoke + debounce Изменения frontend/e2e файлов Автопроверка без блокировки ввода/кодинга
Candidate verify Playwright на отдельно собранном клиентская часть и фиксированной БД Ready MR / merge Однозначное доказательство проверенного коммита

Playwright UI Mode watch документирован для запуска тестов при изменении тестовых файлов. Он не гарантирует выполнение E2E при любом изменении React-кода; для этого предназначен отдельный watcher. Playwright UI Mode.

Процесс наблюдения и ограничение ресурсов

Показать пример кодаBASH
#!/usr/bin/env bash
# scripts/e2e-watch.sh — запускается ОДИН РАЗ в каждом активном worktree.
set -euo pipefail
mkdir -p .runs/e2e
exec watchexec \
  --watch web/src \
  --watch web/tests/e2e \
  --watch packages/ui \
  --debounce 1200ms \
  --on-busy-update=queue \
  --shell=none -- \
  bash scripts/e2e-once.sh

Семантика --on-busy-update=queue: выполнять один тестовый процесс за раз, а изменения во время работы собрать в ещё один прогон после завершения, вместо запуска неограниченного числа Chromium. Debounce фильтрует всплеск сохранений файлов. Watchexec manual.

Показать пример кодаBASH
#!/usr/bin/env bash
# scripts/e2e-once.sh — отчет и статус, не блокируя основной терминал.
set -uo pipefail
mkdir -p .runs/e2e
commit="$(git rev-parse HEAD)"
started="$(date -u +%Y-%m-%dT%H:%M:%SZ)"
if nice -n 10 pnpm exec playwright test --config web/playwright.config.ts --grep @smoke --workers=1 \
     --retries=0 --reporter=line > .runs/e2e/latest.log 2>&1; then
  status=passed
  rc=0
else
  status=failed
  rc=1
fi
printf 'status=%s\ncommit=%s\nstarted=%s\n' \
  "$status" "$commit" "$started" > .runs/e2e/status.tmp
mv .runs/e2e/status.tmp .runs/e2e/status.txt
exit "$rc"

Это рабочий skeleton, адаптируемый к структуре репозитория и package scripts; подключить outputDir Playwright, сохранение screenshot/trace и запуск в фоне через process supervisor/devctl. Отчёт фиксирует HEAD, но не полный хеш незакоммиченных файлов; поэтому не может считаться доказательством точного состояния рабочего дерева. Можно расширить devctl контентным fingerprint всех watched inputs и отмечать отчет как stale, если изменения произошли во время теста.

Изолировать браузер, порт и данные

На каждой активной фиче использовать отдельную DB role/database и URL; один dev server для разработки и отдельный test candidate server для финального smoke. Для background smoke допустим выделенный Vite server без сборки пакета для рабочей среды, если его состояние и тестовые данные предсказуемы. Playwright webServer.reuseExistingServer в финальном gate должен быть false, а URL/порт — однозначно выделены текущему worktree. Иначе тест может «успешно» пройти против чужого уже запущенного сервера. Playwright webServer.

Показать пример кодаTS
// web/playwright.config.ts — укороченный пример.
import { defineConfig } from '@playwright/test';
const port = Number(process.env.E2E_PORT ?? 18103);
const url = `http://127.0.0.1:${port}`;
export default defineConfig({
  testDir: './tests/e2e',
  workers: process.env.CI ? 2 : 1,
  retries: 0,
  outputDir: '../.runs/e2e/results',
  use: {
    baseURL: url,
    trace: 'retain-on-failure',
    screenshot: 'only-on-failure',
  },
  webServer: {
    command: `pnpm exec vite --host 127.0.0.1 --port ${port} --strictPort`,
    cwd: "web",
    url,
    reuseExistingServer: false,
  },
});

Важно: путь testDir и location config относятся к фактической структуре приложения. При финальном gate заменить dev Vite на vite preview после полноценного build; API и БД должны быть фиксированными тестовыми инстансами с проверенными migrations/fixtures.

Соло и команда до пяти: один подход, разная финальная интеграция

В рабочем цикле не должно быть скрытой двойной полной проверки pre-push full verify и затем такого же job в GitLab на том же Mac. make submit подготавливает чистый кандидат и запускает runner; make verify — одна авторитетная реализация обязательного набора.

Точный кандидат и последовательный merge

  1. Координатор получает актуальный main, обновляет ветку и устраняет конфликты.
  2. Замораживает candidate; при необходимости squash делается до проверки.
  3. Runner проверяет конкретный commit (или merged result, где это поддерживается).
  4. Если candidate или base меняется, соответствующий gate запускается снова.
  5. При успехе — fast-forward merge; скрипт сверяет expected commit и current main.
  6. Только после подтверждения очистить worktree/DB/ports.

Состояние main = интегрированная прошедшая проверку версия. Release = версия, прошедшая дополнительные платформенные проверки и опубликованная. Long-lived dev, stage, prod branches не нужны: окружения получают определенный артефакт.

Vercel AI SDK поверх ядра Go

Vercel AI SDK остается необязательной средой выполнения агентов на TypeScript, а не заменяет серверную часть на Go. ToolLoopAgent и инструменты выбирают действия, Go Connect API выполняет операции с проверкой доменных правил и авторизации, а React AI SDK UI отображает поток сообщений. Для настольных приложений использовать удалённый сервис или отдельный вспомогательный процесс, подключаемый по запросу при обосновании автономной работы; мобильные приложения — преимущественно удалённая среда выполнения агента.

Безопасность агента: области разрешений инструментов, одобрение критичных команд, идемпотентность, аудит действий, лимиты токенов/денег, ограниченные циклы вызова инструментов и защита от внедрения инструкций. Длительные задачи не выполнять как единственный цикл LLM: надёжный обработчик задач Go и состояние задач и исходящие события в PG продолжают существовать независимо от AI SDK — см. фоновые задачи River.

Инфраструктура без переписывания: VM + Docker Compose

Первый и основной развёртывание в рабочей среде: Linux VM + неизменяемый OCI-образ Go API + PostgreSQL + обратный прокси (Caddy). Rauthy, RustFS, OpenBao и sync-service подключаются только по выбранному профиль возможностей; для нескольких продуктов предпочтительны общие существующие сервисы. Второй профиль: Kubernetes с тем же Go API image, но другой слой оркестрации. На локальном Mac Docker не нужен. На VM Docker — нормальный способ доставки воспроизводимого приложения.

Правила эксплуатации

  • В Git хранятся манифест Compose, зафиксированные хеши образов, Caddyfile, политики и шаблоны OpenBao, migrations, runbooks и манифест выпуска. Не хранятся секреты рабочей среды в открытом виде.
  • Go API/React можно отдавать из одного Go binary/container, либо выделить статические assets через обратный прокси, если это проще.
  • Миграции — одноразовая отдельная команда до rollout, expand-contract, предварительно проверенная на чистой и предыдущей схеме. down не всегда безопасен: для данных сначала forward-fix и backup plan.
  • Healthchecks для Go API и PostgreSQL; для Rauthy, RustFS, OpenBao — только если включены; readiness отличается от process-alive. depends_on без health не гарантирует готовность приложения.
  • Одна VM не обеспечивает HA: для рабочая среда определить допустимый RPO/RTO, независимые backup stores, PITR и restore-drills. OpenBao требует bootstrap/unseal и план ротации.
  • Для сетевых RPC прокси должен корректно передавать protobuf Content-Type и потоковые ответы; переключение на WebSocket должен быть явным.

Контракт процесса выпуска

commit → tests → buf breaking → go build → OCI/SBOM/signature → migration check → VM deploy via Ansible + Compose → smoke → promote. K8s профиль использует тот же OCI image, migration Job, Secrets integration и metrics.

Сборка для Linux выполняется в CI в целевом окружении, а не копированием бинарника macOS. При CGO или native dependencies нужен воспроизводимый build target с соответствующей libc и arch.

Минимальный пример Compose для Go API

Показать пример кодаYAML
# deploy/compose.yaml — иллюстрация минимального ядра для VM-профиля
services:
  api:
    image: registry.example.com/product/go-api@sha256:REPLACE_WITH_REAL_DIGEST
    restart: unless-stopped
    environment:
      PGHOST: postgres
      PGDATABASE: product
      PGUSER: product
      PGPASSWORD_FILE: /run/secrets/pg_password
    secrets: [pg_password]
    depends_on:
      postgres: { condition: service_healthy }
    expose: ["8080"]
  postgres:
    image: postgres:18
    restart: unless-stopped
    environment:
      POSTGRES_DB: product
      POSTGRES_USER: product
      POSTGRES_PASSWORD_FILE: /run/secrets/pg_password
    secrets: [pg_password]
    volumes: ["pgdata:/var/lib/postgresql"]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U product -d product"]
      interval: 10s
      timeout: 5s
      retries: 10
secrets:
  pg_password: { file: ./secrets/pg_password }
volumes:
  pgdata:

Это иллюстративный основной фрагмент: заменить digest и добавить identity/networking, Caddy, observability, backup, OpenBao Agent, конфигурацию Rauthy и RustFS. Манифест Compose под конкретный продукт заводится при подготовке к развёртыванию; в репозитории платформы на старте готового файла нет. Для PostgreSQL обновление основной версии меняется layout; реальный путь тома сверять с используемым image/tag. POSTGRES_PASSWORD_FILE относится к образ postgres; для собственного API чтение PGPASSWORD_FILE следует реализовать отдельно (или передавать DSN через конфигурацию, подключённую как секрет).

Развёртывание без смены архитектуры: VM Compose первая

Минимальный профиль VM: Caddy/TLS → go-api (собранные ресурсы React встроен через go:embed либо отдается proxy) + PostgreSQL; локальные директории для файлов и secrets. Встроенные River, flags, audit, analytics, notifications, FSM и websocket живут в go-api. Не запускать Rauthy/RustFS/OpenBao/Electric/Umami/Kafka просто потому, что они есть в старом compose; подключать только по выбранному профиль возможностей — см. матрицу возможностей.

Развёртывание profile Контейнеры/внешние зависимости Кому подходит
minimal Go API + PG + обратный прокси; файлы на диске с backup; SOPS secrets Малые standalone продукты
enterprise Go API + PG + существующие shared IdP/S3/OpenBao/monitoring Корпоративные внутренние продукты
offline enterprise + выбранный sync gateway (Electric/PowerSync) Доказанная необходимость offline sync
agent minimal/enterprise + отдельный TS Vercel AI SDK Agent Runtime AI-функции по запросу
scaled реплики Go API / обработчиков задач + broker/HA DB по результатам нагрузки Реальные требования HA и независимого ресурса

Один Docker Compose на одной VM — не HA, независимо от количества контейнеров. Резервные копии PostgreSQL, файлов, ключей и проверенный restore остаются обязательными. OpenBao в рабочая среда требуется полноценный bootstrap/unseal и recovery, а не только контейнер.

Избранные возможности не должны влиять на локальный workflow: интерфейсы OIDC, S3, SMTP и ML заменяются детерминированными тестовыми адаптерами. Kubernetes остается вторым профилем и не определяет структуру доменных пакетов.

Техническая наблюдаемость и бизнес-аудит

Сразу разделять: технический лог, операционная метрика, бизнес-аудит, аналитическое событие. Они имеют разные гарантии, хранение и цели, даже если записываются одним процессом.

Поток Где создаётся Хранение Инвариант
Logs log/slog с request/trace ID stdout → ротация / общий лог-контур Не содержит секретов; запись не меняет результат операции
Metrics prometheus/client_golang /metrics → общий Prometheus при необходимости API latency, error ratio, queue depth, RAM
Traces OpenTelemetry Go, выборочно OTel Collector/shared серверная часть по необходимости Сводит Go handler, SQL и jobs в единую трассу
Business audit Собственный audit модуль PostgreSQL audit_events Сохраняется в транзакции бизнес-изменения
Product analytics analytics usage_events, агрегаты и retention Не блокирует бизнес-транзакцию без бизнес-требования

Вместо Loki, Prometheus или отдельного сервиса логов на каждый продукт приложение отдает совместимый формат существующему общему эксплуатационному контуру. Отдельный мониторинг процесса всё равно необходим для обнаружения полной остановки: умерший серверная часть не сможет сообщить об этом собственным логом.

Аудит: actor_id, action, resource_type, resource_id, organization_id, correlation_id, occurred_at, result, before/after только где это безопасно и необходимо. Обычная таблица не является неизменяемым WORM-хранилищем. При требованиях противодействия администратору — отдельный защищённое хранилище аудита / криптографический журнал.

Политика доверия и управления версиями

  1. Pin commit SHA / release для глобально устанавливаемых навыков в ~/.agents/go-product-platform/global-skills.lock.json; main в таблице — ссылка для чтения, не зафиксированная dependency.
  2. Проверять исполняемые скрипты, shell-команды, сетевые обращения и инструкции изменения конфигурации. Не давать сторонним навыкам доступ к учётным данным рабочей среды.
  3. Контролировать неявные обновления: web-design-guidelines загружает текущие правила из сетевого источника при каждом ревью; для воспроизводимости заменить URL на фиксированный commit/локальную копию, прежде чем включать в автономный pipeline.
  4. Учитывать drift API: особенно Wails 3, Connect-Go v2 и mobile SDK. Авторитетнее инструкций навыков — документация установленной версии, компилятор и проверяемый тест.
  5. Любое обновление навык проходит тестовый fixture: агент решает типовую задачу → запускает standard gates → сравниваются исправления, regressions, latency и затраты токенов. Результат должен быть воспроизводим.
  6. Контролировать, чтобы навык не заменял архитектурные правила: KISS, YAGNI, права, audit, isolation worktree и module владение задаются в AGENTS.md и контрольных проверках качества.

Внутренние надстройки, которые ещё нужно реализовать: wails3-desktop, connectrpc-v2, mobile-connect-protobuf, local-native-devctl, modular-monolith-fitness. Для них пока нет самостоятельных GitHub-ссылок: это проектные задачи, а не выдаваемые за готовые публичные навыки. Их инструкции должны быть короткими и ссылаться на существующие стандарты документа, чтобы не копировать всю архитектуру внутрь промптов.

Если навык должен переиспользоваться членами команды, его осознанно публикуют как версионируемый артефакт проекта, а не автоматически превращают в глобальное правило для всех продуктов.

Воспроизводимость и границы безопасности

  • Два независимых lock-файла: проектный go-product-platform.lock.json фиксирует версию платформы; пользовательский ~/.agents/go-product-platform/global-skills.lock.json фиксирует SHAs общих навыков.
  • Управляемые обновления: переустановка другого main из GitHub не должна молча менять инструкции во всех проектах; глобальное обновление — отдельная осознанная операция с тестом.
  • Изоляция: глобальные навыки являются руководствами для агента, но сами по себе не получают учётные данные рабочей среды; графы и результаты проверок не общие между worktree.
  • Проверка: gpp doctor --strict определяет отсутствие обязательных глобальных навыков, неправильную настройку orca.yaml и оставшиеся ссылки v13.

Контракт управления и CLI для агентов

В отличие от большого скрипта с побочными эффектами, управление разбито на команды с разными разрешениями. Команды исполняет агент; они приведены в аккордионах как архитектурный интерфейс.

Показать пример кодаSH

gpp skills-inventory --project . --json

# Зафиксировать профиль продукта после согласия пользователя.
gpp skills-activate --project . --profile web --approve

# Установить именно указанные curated skills глобально после согласия.
gpp skills-install-global --names golang-testing,protobuf,shadcn --approve

# Для Graphify и Orca использовать официальные установщики (подтверждение отдельно).
gpp skills-install-external --names graphify,orca-cli --approve

Для проверки и актуализации навыков:

Показать пример кодаSH

Старые снимки сохраняются. Если актуализация вызывает конфликт с пользовательским навыком, она останавливается без принудительной замены.

Особенность обновления каталога: проверка отслеживает уже закреплённые Git-источники. Новые имена навыков, которых ещё нет в манифесте Go Product Platform, включаются через отдельное версионированное обновление каталога платформы; они не устанавливаются автоматически только из-за того, что появились на GitHub.

Глобальные изменения и совместимость между проектами

Обновление навык влияет на все проекты на машине, потому что все они используют одну глобальную копию. Поэтому управляющий agent обязан показать:

  • какие навыки и проекты потенциально затронуты;
  • ссылки на источники и старый/новый commit SHA;
  • меняется ли команда установки/запуск скриптов;
  • план проверки после обновления и путь восстановления прежнего snapshot;
  • какие навыки обслуживаются независимо (Orca/Graphify) и не покрываются обновлением снимков курируемых Git-репозиториев.

Чтобы проверка обновлений не влияла на кратчайший девелоперский цикл, ее запускают только по просьбе пользователя (либо после отдельно согласованной политики), а не в orca.yaml и не при каждом создании worktree. Orca умеет управлять собственными глобальными навыками через встроенный updater; команду orca skills update следует запускать с явным согласованием. Для Graphify используется официальный uv tool upgrade graphifyy.

Воспроизводимость и миграция с v14

Уже установленная v14 не обновляется скрыто: новый доверенный стартовый набор сначала заменяет CLI, затем агент предлагает явную миграцию проекта и согласование его активного профиля. Все AGENTS.md, существующие уникальные проектные навыки, индивидуальные hooks Orca и пользовательские глобальные навыки сохраняются.

Показать пример кодаSH

Правила совместимости и миграций

  • API: .proto versioned packages (v1, v2), Buf breaking, период поддержки выпуска; совместимость клиентов без прямого изменения типы данных в протоколе.
  • DB: расширение и последующее сужение схемы, план отката, отдельно PostgreSQL/SQLite, миграции без потери данных.
  • Sync: revision/cursor, повторные команды без дублей, snapshot после истечения период повторного воспроизведения.
  • Desktop/mobile: подписанные релизы; старый клиент не должен ломаться от серверного deploy; приложение может работать с устаревшим token/session.
  • UI: versions собственных дизайн-токенов и компонент registry; обновления без лавины визуальных регрессий.
  • AI tools: версия схемы, область разрешений, тесты инвариантов, одобренные побочные эффекты.

См. также: правила эволюции схем, deployment policies.

Эталонный путь внедрения (v11)

Этап A — локальный фундамент. Один шаблон репозитория; Go 1.27.4/PG18.7/mise/pnpm, make bootstrap/dev/check, один worktree с нативным PostgreSQL, быстрые модульные/компонентные тесты. Измерить цикл с прогретыми кэшами.

Этап B — воспроизводимый e2e-фон. Отдельный проект Playwright для каждого рабочего дерева, наблюдение через watchexec, один процесс Chromium и собственная БД, трассировка и снимок экрана, статус и отметка об устаревании. Сначала 3–5 реальных пользовательских сценариев.

Этап C — встроенные сервисные возможности. Добавлять модуль за модулем по реальным требованиям: профили и доступ, аудит, River, FSM, уведомления, аналитика, флаги, поиск. Переиспользуемый реестр модулей времени компиляции, без централизованных микросервисов.

Этап D — одна финальная проверка перед слиянием. Зафиксированный кандидат, общий набор verify, локальный исполнитель GitLab на Mac для соло-разработки или общий исполнитель в команде, слияние fast-forward, защита main. Перестать дублировать полный прогон в pre-push.

Этап E — релиз и эксплуатация. OCI Go + React, минимальный Compose на VM, резервное копирование/PITR, защищённые секреты, общий мониторинг, базовые проверки, откат. Подписание нативных настольных и мобильных приложений — отдельные платформенные проверки. K8s — при измеренной потребности.

Критерии готовности: агент может открыть URL worktree, получить тестовый контекст, реализовать изменение, увидеть отрицательный и положительный тест, получить трассировку E2E, предъявить отчет готового кандидата; тот же коммит проходит финальную проверку и поставляется как проверенный артефакт.

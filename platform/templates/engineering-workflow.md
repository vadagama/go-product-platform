# Правила разработки с агентами

Обязательная основа продукта — структура документации и workflow Go Product Platform
(главы 19–20 руководства). Адаптации фиксируются в этом документе с обоснованием.
Документы продукта хранятся в Git под docs/, материалы платформы — в установке навыка
go-platform-bootstrap и глобальных каталогах агента.

Порядок: specify → design → plan → implement → verify → review → ready → released.
Каждая фича находится в `docs/specs/<SPEC-ID>/`: requirements, design, plan, tasks,
verification, review. Артефакты — обычный Markdown с YAML frontmatter (контракт — глава 20
руководства); исполняемых ворот нет, дисциплину обеспечивают эти правила, ревью и Git-история.

Формат артефактов задаётся шаблонами software-development-workflow
(`.agents/references/software-development-workflow/templates/`, для Claude — те же пути
в `.claude/references/`), метод и ворота — навыками набора в `.agents/skills/` и
`.claude/skills/`. Соответствие документов каталога:

| Документ | Шаблон SDW | Навык (метод, ворота) |
|---|---|---|
| HLD | `hld.md` | — |
| ADR | `adr.md` | documentation-and-adrs |
| SPEC: requirements, design | `spec.md` — у стандарта единый документ | spec-driven-development |
| SPEC: plan | `plan.md` | planning-and-task-breakdown |
| SPEC: tasks | `tasks.md` | planning-and-task-breakdown, incremental-implementation |
| SPEC: verification | — | test-driven-development |
| SPEC: review | — | code-review-and-quality |
| Контракт API | `api.md` — только семантика, схема в `.proto` | — |
| Модель данных | `data.md` — только семантика, схема в миграциях | — |
| Реестр `docs/agent-skills.md` | — | — |
| `MANUAL.md` | — (близок `product-readme.md`, но это ops-команды) | — |

Осознанные отличия: verification и review не имеют шаблонов SDW — доказательства проверок
и независимое ревью обязательны для процесса; requirements и design разделены вместо
единого `spec.md`; карта возможностей (`capability-map.md`, фаза 0 spec-driven-development)
применяется при разбиении крупной инициативы без отдельного места в каталоге; шаблоны
`lld.md`, `constraints.md`, `events.md`, `debt.md`, `initiative.md` — по необходимости
в порядке главы 20 руководства. После обновления software-development-workflow сверьте
таблицу с его `templates/`: расхождение каталогов — сигнал пересмотреть адаптации здесь.

Прежде чем писать код, зафиксируйте требования с уникальными AC-ID, границы и влияние на
документацию; затем дизайн (решение, альтернативы, риски) и план с вертикальными срезами-задачами
(T-ID, зависимости, проверка каждого среза). Не разбивайте фичу на очереди «вся БД», «весь
backend», «весь frontend».

Доказательства: запускайте реальные проверки (unit/e2e/contract) и фиксируйте команду, результат
и покрытие AC в verification.md. Старый зелёный отчёт не считается доказательством нового
кандидата: после смены кода, требований, дизайна, архитектуры, плана или ребейза
проверки прогоняются заново. Последующий коммит только с verification/review и ссылками
на результаты допустим без повторного прогона, если проверяемые входы не изменились.
В отчёте сохраняйте SHA проверенного кандидата; новый SHA не объявляйте проверенным. Изменение
утверждённых требований/дизайна/плана означает новый цикл с пересогласованием; для выпущенных
фич создавайте delta-spec с новым ID и related на исходную SPEC.

Автономия: low/medium-риск в согласованном объёме агент проходит сам. Высокий риск (разрушительные
миграции, границы доверия, архитектура) и любой выпуск требуют фактического решения человека;
агент не выдумывает одобрения и не понижает риск. Ревью выполняет другая сессия/человек с отдельным
контекстом; ревьюер не исправляет код сам.

Один владелец фичи и один пишущий агент на worktree; параллелизм — между независимыми фичами.
tasks.md — единственный список задач; не создавайте второй источник истины. Принятые ADR не
переписываются: новое решение — новый ADR с supersedes. Не выдавайте draft HLD за реализованную
архитектуру. API — .proto, данные — миграции; Markdown описывает семантику, а не копирует схемы.

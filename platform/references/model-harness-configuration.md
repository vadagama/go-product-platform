# Модели и харнесы по ролям

Модель, провайдер и харнес — разные настройки. Claude, DeepSeek и GLM обозначают
семейства моделей; точный model ID зависит от провайдера. Codex, Claude Code и
OpenCode — среды выполнения. Название «Codex» также может встречаться в имени
модели: всегда уточнять оба поля. Не предполагать, что любая модель работает
в любом харнесе. DeepSeek/GLM можно назначить через совместимый OpenCode-провайдер
после проверки доступности. Если пользователь имеет в виду другой CLI, записать
его как отдельный харнес и проверить его адаптер.

Это инструменты **разработки**, независимо от наличия AI-функций в продукте.
Набор навыков определяет процесс; назначение модели определяет исполнителя.

## Контракт engineering.yaml

Канонический формат — [шаблон schema 1.1](../templates/engineering.yaml).
`ai.harnesses` перечисляет активные среды. `ai.assignments` содержит уникальные
назначения: id, harness, provider, model, variant, status, config_paths, launch,
verification. `ai.roles` ссылается на id назначения; одно назначение может обслуживать
несколько ролей. Все семь ключей обязательны для новой настройки:

| Роль | Работа и выходные материалы |
|---|---|
| `documentation` | Документация и MANUAL, актуализация знаний |
| `code` | Реализация и тесты кода |
| `ui` | Дизайн и реализация целевого UI и прототипов, docs/ui |
| `code_review` | Независимое ревью кода, findings в review.md |
| `design_review` | Независимое UX/визуальное ревью работающего UI |
| `requirements` | Интервью, гипотезы, REQ/AC, requirements.md |
| `architecture` | HLD, ADR, технический design.md SPEC |

`null` означает «не выбрано», не автоматический default. Для продукта без UI
можно оставить ui/design_review null с причиной в MANUAL. Для прочих применимых
ролей нужно конкретное назначение. `variant` опционален и используется только
если выбранная среда его поддерживает. Не подставлять «latest» или вымышленные ID.
Ключи и токены не хранятся в YAML, prompts или Git; сохраняются только ссылки на
настройку аутентификации и имена переменных без значений.

`configured` — файлы подготовлены, `verified` — фактический запуск подтверждён,
`blocked` — указана конкретная причина. `config_paths` указывает реальные
отслеживаемые адаптеры (либо пустой список для ручного выбора); `launch` содержит
проверенный способ выбора в CLI/desktop. `verification` ссылается на запись в MANUAL
с версией харнеса, датой, назначением и результатом запуска. Сам файл engineering.yaml
не переключает модель и не является исполняемым orchestrator.

## Первоначальная настройка

1. Прочитать текущие настройки и доступные сведения среды. Выяснить предпочтения:
   одна модель для всех ролей, распределение по ролям или сохранение текущих.
   Уже названные модели/харнесы не спрашивать повторно.
2. Для каждой применимой роли показать таблицу «роль → харнес → провайдер → model ID
   → variant → способ запуска». При выборе семейства уточнить точную доступную
   модель по каталогу выбранной среды. Предложить конкретный набор по доступности
   пользователя; платформа не закрепляет универсальную «лучшую» модель.
3. Проверить совместимость, версии CLI, авторизацию и возможность tools/skills;
   для дизайн-ревью — доступ к визуальному результату. Настройка новых аккаунтов
   или оплачиваемых сервисов входит в план только при соответствующем запросе.
4. Подготовить назначения и адаптеры. Общие правила — AGENTS.md, Claude Code —
   тонкий CLAUDE.md, OpenCode — [свой адаптер](opencode-installation.md).
   Для Codex/Claude Code использовать документацию установленной версии, нативный
   выбор модели/профиль/роль. Не копировать настройки OpenCode в другие харнесы.
   Если автоматический выбор недоступен, записать точный ручной запуск и handoff.
   Адаптер создаётся по роли, даже если несколько ролей используют одно назначение:
   модель может совпадать, а инструкции и права — различаться.
5. Применить согласованный план, сохранив пользовательские настройки. Проверить
   каждое уникальное назначение короткой задачей без изменения продукта:
   модель/провайдер, чтение AGENTS, обнаружение нужных навыков и доступные tools.
   Не запускать весь цикл разработки ради smoke. Нет доступа — `blocked`, а не
   фиктивное `verified`; независимые шаги настройки продолжаются.

## Маршрутизация и передача работы

Перед этапом агент читает `ai.roles` и выбирает назначение. Если текущая сессия
не соответствует ему, использует поддерживаемое переключение/делегирование или
готовит передачу в другой харнес. Нельзя заявлять, что другая модель выполнила
работу, если текущая сессия просто прочитала её роль. `fallback: ask` запрещает
молчаливую замену; уже разрешённая пользователем замена не требует нового вопроса.

Передача содержит SPEC/T-ID (либо PROTOTYPE-ID), исходный commit и рабочее дерево,
цель, разрешённые файлы, контекст и критерии, команды проверок, фактический diff
и оставшиеся вопросы. В MANUAL описать способ запуска каждого назначения;
в verification/review — фактического исполнителя, модель, харнес и проверенный SHA.
Не допускать одновременной записи разными харнесами в одни файлы без разделения
владения. Перед сменой исполнителя сохранить незакоммиченные изменения.

Роли автора и reviewer могут использовать одну модель, но ревью проходит в отдельной
сессии/контексте. Разные названия моделей сами по себе не доказывают независимость.
При совмещении `ui` и `code` явно назначить владельца реализации интерфейса;
`documentation` оформляет решения, принятые requirements/architecture/ui.

## Перенастройка существующего продукта

Точка входа — `go-project-platform-manager`: «замени модели/харнесы» или
«подключи OpenCode». Это отдельная операция от обновления навыков и UI-миграции.

1. Осмотреть engineering.yaml, AGENTS/CLAUDE, проектные конфигурации, активные
   назначения и Git diff. Глобальные настройки не изменять и не сканировать
   без необходимости и разрешения. Не запускать полный bootstrap повторно.
2. Показать таблицу старое → новое по затронутым ролям, конкретный diff адаптеров,
   зависимости/аутентификацию, проверки и откат. Сохранить неизменяемые роли,
   документы, навыки и версии. Уже разрешённый объём выполнить без повторного опроса.
3. Сохранить прежние файлы и локальные изменения; новые настройки вносить только
   в управляемые поля/файлы. Чужие agent IDs, permissions, MCP и provider config
   сохранять. Не удалять конфигурацию прежнего харнеса, если её используют другие
   роли; не отключать активные сессии автоматически.
4. Обновить назначения, адаптеры, инструкции и MANUAL вместе. Старые назначения
   удалить из активного списка только когда на них не ссылается ни одна роль.
   Запустить проверки новых назначений и убедиться, что остальные не изменились.
5. При сбое сохранить отчёт и рабочую прежнюю конфигурацию; по плану откатить
   только собственные изменения. Если оставлен частичный переход, явно отметить
   `configured`/`blocked` и не объявлять перенастройку завершённой.

Повторное применение не дублирует агенты и конфиги. Проверка «только посмотреть»
ничего не меняет. Для schema 1.0 отсутствие ai означает «не настроено»: добавить
блок и поднять engineering schema до 1.1 после выбора; не менять product schema.

## Приёмка

Все ссылки roles разрешаются, id уникальны, harness включён в harnesses.
Каждый путь config_paths существует; все применимые назначения имеют проверенные
model ID, способ запуска и честный status. Маршрутизация совпадает с адаптерами;
проверены handoff и независимость reviewer. В свежем clone/worktree доступны
отслеживаемые настройки; credentials и CLI восстанавливаются отдельно. Сохранён
откат и не затронуты несвязанные настройки. Отчёт перечисляет непроверенные роли.

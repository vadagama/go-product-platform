# Реверс-инжиниринг продукта

Работай в исходном репозитории продукта. Для Git URL используй локальный checkout. Прочитай инструкции проекта и карту документации. Сохрани существующие материалы и незакоммиченные правки. Обновляй подходящие страницы на месте. Результат должен читаться из свежего клона без доступа к чату, абсолютным путям машины или базе индексатора.

## Инвентаризация и граф

1. Зафиксируй ревизию, значимые локальные отличия, модули, языки, способы сборки, точки входа, экраны, фоновые задачи, хранилища, интеграции и источники требований. Заведи таблицу покрытия по подсистемам с источниками, статусом проверки, ссылками на узлы и страницы. Укажи исключённые каталоги и причины.
2. Для каждого Go-модуля выполни загрузку пакетов, `gokg analyze --tests` и `gokg stats`. Запросами извлеки пакеты, символы, вызовы и реализации интерфейсов, связывай результаты с файлами и тестами. Сверяй неполные результаты с условиями сборки и динамической регистрацией. При отсутствии Go отметь неприменимость. При ошибке загрузки укажи затронутые пакеты и продолжи разбор доступных исходников. [Установка и запросы GoKG](../../references/gokg-installation.md)
3. Через навык Graphify построй направленный граф кода и документов, включая конфигурацию, тесты, UI и схемы. Используй семантическое извлечение для документов. Проверь состав входов по manifest. Исключи зависимости, кеши, секреты и сами экспорты. После написания документации обнови граф семантически и проверь новые, изменённые и удалённые входы. [Порядок работы с Graphify](../../references/graphify-installation.md)
4. Соедини результаты по пути файла, модулю и полному имени символа. Сохрани в дереве документации версионируемый машиночитаемый граф и визуальную карту подсистем со ссылками на детали. Для узла укажи стабильный ID, вид и источник, для ребра — начало, конец, тип, инструмент и основание. Различай извлечённые, предполагаемые и спорные связи. Включи маршруты от пользовательского действия или события через код до данных и видимого результата. Проверь направления по исходникам. Приведи воспроизводимые запросы Graphify query/path и GoKG с ожидаемыми узлами.

## Комплект документации

Сделай `docs/README.md` точкой входа с маршрутами для пользователя, оператора и разработчика. Используй структуру GitLab Docs: обзор возможности ведёт к пошаговой задаче, справочнику и связанным темам. Каждой странице дай содержательный заголовок и стабильную ссылку. Добавь полнотекстовый поиск с переходом к разделу через существующий генератор документации. При его отсутствии создай локальный поисковый указатель HTML с встроенным индексом заголовков и текста и относительными ссылками на страницы и якоря. Опиши запуск из клона. [Образец навигации GitLab Docs](https://docs.gitlab.com/devsecops/)

| Раздел | Что восстановить и чем проверить |
|---|---|
| HLD | Контекст, акторы, границы, компоненты, владельцы данных, интеграции и развёртывание. Нарисуй контекст и связи компонентов, сопоставь их с конфигурацией запуска. |
| ADR | Для каждого существенного решения опиши контекст, выбор, последствия, статус и свидетельство. Сохрани исторические ADR. Восстановленное решение пометь явно, неизвестную мотивацию или альтернативы оставь открытыми. |
| LLD | По каждому модулю укажи входы, зависимости, алгоритмы, состояния, транзакции, параллелизм, ошибки и повторные попытки. Покажи sequence/state-диаграммы важных путей и небольшие фрагменты кода со ссылками на символы. |
| API и события | Сопоставь каталог операций с фактической регистрацией. Зафиксируй протокол, права, параметры, схемы, ответы и ошибки, версии, пагинацию и повторные вызовы там, где они применимы. Свяжи с OpenAPI, proto или схемой события. При отсутствии спецификации восстанови её в подходящем машиночитаемом формате. Добавь проверенный пример обмена. |
| Объекты данных | Дай словарь сущностей и полей, типы, ключи, обязательность, ограничения, связи, состояния и жизненный цикл. Построй ER-схему, сверь модель с миграциями, сериализацией и правилами в коде. |
| UI | Составь карту экранов, переходов, ролей и действий. Опиши состояния загрузки, пустого результата, успеха, ошибок и ограничения ввода. Свяжи экран с операцией и данными. Добавь иллюстрации с подписями: обезличенные снимки доступного UI либо явно подписанные реконструкции по компонентам. |
| MANUAL | Дай воспроизводимые команды установки, настройки, запуска, проверки состояния и диагностики. Для поддерживаемых операций опиши резервирование и восстановление. Различай выполненные проверки и команды, восстановленные из конфигурации. |
| User guide | Проведи читателя каждой роли от предпосылок до наблюдаемого результата. Покажи основной сценарий, частую ошибку и способ восстановления, свяжи шаги с иллюстрациями UI или примером работы клиента. |

В продукте платформы используй HLD и тематические страницы внутри `docs/hld/`, ADR в `docs/adrs/`, корневой MANUAL и существующие SPEC/UI-страницы. Подробности действующей реализации без соответствующей SPEC размести на тематической странице HLD. В остальных продуктах следуй принятой структуре. Включи в Git-дерево исходники схем, иллюстрации, спецификации, поисковый индекс или рецепт его сборки и инструкцию обновления графа. Для отсутствующей поверхности (например, UI у библиотеки) запиши основание в карте покрытия.

## Передача для разработки на другом стеке

Для каждой возможности составь цепочку «роль → предусловия → действие → наблюдаемый результат → контракт → источник/тест». Опиши инварианты независимо от фреймворка. Укажи, какие детали обусловлены текущей реализацией. Дай переносимые примеры входов и ожидаемых выходов для обычного случая, границ, отказов и повторов. Неизвестное поведение и противоречия вынеси в список вопросов со способом проверки.

Перед сдачей сопоставь таблицу покрытия с исходной инвентаризацией. Проверь уникальность ID, концы рёбер, пути к исходникам, относительные ссылки, якоря, рендеринг схем и валидность спецификаций. Из собранной документации найди по термину из тела страницы конкретный раздел и пройди один пользовательский сценарий до теста или кода. В отчёте укажи точку входа, пути к графу и спецификациям, ревизию и оставшиеся пробелы. При неполном покрытии обозначь результат как частичный.

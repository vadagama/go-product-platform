# Опросник настройки в чате

Вход: `/go-platform-bootstrap Подготовь этот проект к разработке` в целевом
Git-репозитории. В ADE с другой формой вызова меняется только упоминание скилла.
Пользователь не запускает команды, не заполняет конфиги и не выбирает технические
имена профилей. Агент ведёт диалог, затем сам устанавливает согласованный набор.

## Правила диалога

- Один вопрос за раз. Короткие варианты с рекомендуемым выбором и свободным ответом.
- Для вопросов используйте доступный инструмент ввода ADE; если его нет — чат.
  Не вызывайте недоступный инструмент и не переключайте режим ADE ради опроса.
- Сначала прочитайте README, правила и manifests продукта, платформенный lock и
  setup-контракт, если они есть. Не меняйте файлы и не обращайтесь к сети.
- Учитывайте явно заданные ответы; для найденного в коде предложите подтверждение
  рекомендации. Не отправляйте пользователя разбираться в стеке или CLI.
- После ответа переходите к следующему применимому вопросу. Неприменимые вопросы
  пропускайте. Не повторяйте уже разрешённое действие и не включайте обновление
  всех глобальных skills в первоначальную настройку.
- Если пользователь отменяет до применения, остановитесь без записей. При отказе
  в глобальном осмотре не заявляйте наличие/отсутствие skills: предложите настройку
  только материалов проекта и объясните, что полная готовность останется непроверенной.

## Последовательность

### 1. Продукт

Если цель неясна из запроса/README: «Что делает продукт и для кого? Достаточно
одного-двух предложений». Если цель известна, кратко используйте её как контекст.
В существующем проекте по умолчанию сохраняйте код, пользовательские файлы и стек;
новый запрос настройки не означает разрешение на переписывание приложения.

### 2. Целевые приложения

«Где должен работать продукт?» Варианты: браузер, настольное приложение,
мобильное приложение, только сервер/API, несколько платформ. Если интерфейс ADE
ограничивает число вариантов, задайте короткий вопрос текстом вместо усечения выбора.
Для mobile уточните iOS, Android или обе — только если ответ ещё не известен.
Для нескольких платформ выясните первый запускаемый клиент; остальные укажите
отдельными этапами плана, не называйте весь набор готовым после проверки одного.

Соответствие для агента: браузер → web, desktop → desktop, mobile → mobile-native,
сервер → go-api. Если ответ требует комбинации, используйте ближайший базовый
профиль с дополнительными skills/components; не теряйте выбранные пользователем цели.

### 3. Стек и локальное окружение

Предложите один понятный набор по ответам и handbook:
«Предлагаю Go и PostgreSQL для сервера, React для браузера, API через Protobuf/Connect.
Подходит стандарт платформы или есть ограничения?» Для desktop — Wails, для mobile —
выбранный SwiftUI/Compose; перечисляйте только нужные части. В существующем продукте
рекомендация — дополнить найденный стек, а не заменить его.

ОС и уже видимые версии определите сами. Уточните только неизвестное, влияющее на
установку: локальная или удалённая dev-БД, ограничение доступа/установки, требуемые
платформы сборки. Запишите адаптации в план. Не спрашивайте пароли и токены в чате.

### 4. Опциональные возможности

Только при необходимости выясните AI-функции и провайдера. При выборе AI для web
используйте профиль ai; для другого клиента добавьте нужные AI skills/components.
Для UI предложите canvas: «Подключить визуальную среду дизайна app-canvas?»
Ответ «нет» не блокирует обычную настройку UI. При согласии локальный клон
проверяет/готовит агент; спрашивайте пользователя только о недоступном доступе.
Не требуйте от пользователя вручную клонировать репозиторий или выполнять установку.

### 5. Инвентаризация

«Можно проверить установленные инструменты и глобальные навыки, чтобы использовать
существующие и установить только недостающие?» Это проверка без изменений;
пользователь выбирает «Проверить» или «Без проверки глобальных навыков».
Если уже разрешено — не спрашивайте снова. После согласия выполните inventory
и локальные version probes. Список новых навыков формируйте по выбранному набору,
Graphify включайте всегда; для Orca предложите нужные официальные Orca skills.

### 6. Итоговый план

До запроса применения самостоятельно подготовьте конкретный план: выбранные
совместимые версии и источники, известные отсутствующие инструменты/skills,
планируемые файлы/генераторы и команды проверок. В памяти/выводе CLI можно собрать
JSON без записей, пользователь его не редактирует. Если версии нужно проверить
по сети, согласуйте такой просмотр в рамках диагностики.

Покажите короткое человеческое описание:

- Продукт и целевые приложения.
- Стек, локальная среда и способ запуска.
- Стандартный процесс требований, дизайна, реализации, проверки и ревью.
- Документы и конфигурация, которые появятся/будут дополнены в Git.
- Точные глобальные инструменты/навыки для установки и источники; уже установленные
  будут использованы. Обновления существующих навыков — отдельное решение.
- Опциональные компоненты и проверки готовности; известные ограничения.

Спросите один раз: «Применить этот план настройки?» Варианты: «Настроить»,
«Изменить выбор», «Отменить». Этот ответ разрешает только показанный объём.
Если пользователь заранее одобрил именно этот конкретный объём, достаточно
показать итог и продолжить. «Изменить» возвращает к затронутому вопросу.

## После опроса

Агент сам записывает setup-контракт, подготавливает недостающий код и конфигурацию,
выполняет `init --setup-plan … --approve` и `doctor --ready` через runner скилла.
Пользователю показывает ход работы и итог: что готово, как запускать продукт,
какие проверки прошли. При блокере продолжает независимую работу, задаёт только
необходимый вопрос и не объявляет окружение полностью готовым.

Возобновление: читайте предыдущие ответы в чате и существующий контракт продукта,
спрашивайте только изменившиеся/незаполненные параметры. Не запускайте опрос заново
для простого запроса проверки или обновления навыков.

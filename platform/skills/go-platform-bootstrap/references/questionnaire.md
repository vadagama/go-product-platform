# Опросник настройки в чате

Вход: `/go-platform-bootstrap Подготовь этот проект к разработке` в целевом
Git-репозитории. В ADE с другой формой вызова меняется только упоминание скилла.
Пользователь не запускает команды, не заполняет конфиги и не выбирает технические
имена профилей. Агент ведёт диалог, затем сам устанавливает согласованный набор.

## Правила диалога

- Один вопрос за раз. Короткие варианты с рекомендуемым выбором и свободным ответом.
- Для вопросов используйте доступный инструмент ввода ADE; если его нет — чат.
  Не вызывайте недоступный инструмент и не переключайте режим ADE ради опроса.
- Сначала прочитайте README, правила и реестр набора `docs/agent-skills.md`, если он есть. Не меняйте файлы и не обращайтесь к сети.
- Учитывайте явно заданные ответы; для найденного в коде предложите подтверждение
  рекомендации. Не отправляйте пользователя разбираться в стеке или CLI.
- После ответа переходите к следующему применимому вопросу. Неприменимые вопросы
  пропускайте. Не повторяйте уже разрешённое действие и не включайте обновление
  всех глобальных skills в первоначальную настройку.
- Если пользователь отменяет до применения, остановитесь без записей. При отказе
  в глобальном осмотре не заявляйте наличие/отсутствие skills: предложите настройку
  только материалов проекта и объясните, что полная готовность останется непроверенной.

## Последовательность

### 1. С чего начать

После осмотра репозитория первым вопросом спросите: **«С чего вы хотите начать?»**

1. **Подготовить проект к разработке.** Выбрать стек и окружение, установить всё
   необходимое для начала разработки. Описание продукта можно добавить позже.
2. **Описать идею нового продукта.** Рассказать о продукте несколькими предложениями,
   уточнить первую версию и настроить проект под неё.
3. **Разобрать готовые требования.** Прикрепить документы или дать ссылки;
   сначала согласовать понимание требований, затем настроить проект.

Не выбирайте путь по умолчанию. Если намерение уже явно указано в запросе,
назовите выбранный путь и продолжайте без повторного вопроса. Наличие README или
кода само по себе не определяет путь. Сохраняйте существующий код, пользовательские
файлы и стек во всех трёх путях; подготовка проекта не означает очистку репозитория.

#### Подготовить проект к разработке

Переходите к целевым приложениям и короткому техническому опросу ниже. Не требуйте
описания пользователей, бизнес-функций или границ MVP. По выбранному стеку
подготовьте инструменты, зависимости, структуру, правила, навыки и минимальную
запускаемую основу с реальными проверками. Не ограничивайтесь документацией.
Не придумывайте предметную область и функциональность: SPEC настройки описывает
только техническую основу, а HLD отмечает, что контекст продукта ещё не определён.

#### Описать идею нового продукта

Спросите: «Что делает продукт и для кого? Достаточно нескольких предложений».
Используйте уже данное описание; уточняйте по одному вопросу только то, что влияет
на первую версию и настройку. Кратко сформулируйте пользователей, основную задачу
и границы первой версии, затем переходите к целевым приложениям.

#### Разобрать готовые требования

Попросите прикрепить документы или дать ссылки на требования, если они ещё не
предоставлены. Для вложений используйте обычный чат, а не инструмент с текстовым
полем ответа. Прочитайте все предоставленные материалы доступными средствами;
ссылки открывайте для чтения. Если источник недоступен, назовите его и попросите
доступную копию или выдержку, не подменяйте его предположениями.

Сначала покажите короткое резюме понимания: назначение и пользователи продукта,
функциональные и нефункциональные требования, ограничения и границы первой версии.
Для выводов укажите исходный документ/раздел или ссылку; отдельно обозначьте
предположения, противоречия и пробелы. Не повторяйте вопросы, на которые материалы
уже отвечают. Уточняйте существенные неизвестные по одному вопросу; при конфликте
источников выясните, какой из них актуален.

До выбора окончательного стека и плана настройки спросите: «Верно ли я понял
требования?» Дождитесь ответа, внесите исправления и только затем продолжайте
общий опрос. Подтверждение понимания требований не является разрешением установки.
После согласования плана сохраните результат анализа в документах продукта под
`docs/` по главам 19–20: требования, источники и принятые уточнения. Полные исходные
вложения не добавляйте в Git автоматически. Настройка готовит основу разработки,
а не реализует все функции из требований.

Все три пути продолжаются вопросами 2–6 и общей настройкой с [чек-листом готовности](product-setup.md#критерии-готовности).
Пропускайте вопросы, ответы на которые уже известны из запроса или требований.

### 2. Целевые приложения

«Где должен работать продукт?» Варианты: браузер, настольное приложение,
мобильное приложение, только сервер/API, несколько платформ. Если интерфейс ADE
ограничивает число вариантов, задайте короткий вопрос текстом вместо усечения выбора.
Для mobile уточните iOS, Android или обе — только если ответ ещё не известен.
Для нескольких платформ выясните первый запускаемый клиент; остальные укажите
отдельными этапами плана, не называйте весь набор готовым после проверки одного.

Соответствие для агента: браузер → web, desktop → desktop, mobile → mobile-native,
сервер → go-api. Если ответ требует комбинации, используйте ближайший базовый
профиль с дополнительными skills/components; не теряйте выбранные пользователем цели.

### 3. Стек и локальное окружение

Предложите один понятный набор по ответам и handbook:
«Предлагаю Go и PostgreSQL для сервера, React для браузера, API через Protobuf/Connect.
Подходит стандарт платформы или есть ограничения?» Для desktop — Wails, для mobile —
выбранный SwiftUI/Compose; перечисляйте только нужные части. В существующем продукте
рекомендация — дополнить найденный стек, а не заменить его.

ОС и уже видимые версии определите сами. Уточните только неизвестное, влияющее на
установку: локальная или удалённая dev-БД, ограничение доступа/установки, требуемые
платформы сборки. Запишите адаптации в план. Не спрашивайте пароли и токены в чате.

### 4. Опциональные возможности

Только при необходимости выясните AI-функции и провайдера. При выборе AI для web
используйте профиль ai; для другого клиента добавьте нужные AI skills/components.
Для UI предложите canvas: «Подключить визуальную среду дизайна app-canvas?»
Ответ «нет» не блокирует обычную настройку UI. При согласии локальный клон
проверяет/готовит агент; спрашивайте пользователя только о недоступном доступе.
Не требуйте от пользователя вручную клонировать репозиторий или выполнять установку.

### 5. Инвентаризация

«Можно проверить установленные инструменты и глобальные навыки, чтобы использовать
существующие и установить только недостающие?» Это проверка без изменений;
пользователь выбирает «Проверить» или «Без проверки глобальных навыков».
Если уже разрешено — не спрашивайте снова. После согласия осмотрите
`~/.agents/skills/` и `~/.claude/skills/` и выполните локальные проверки версий
(`go version`, `node --version`, `uv tool list` и т.п.). Список новых навыков
формируйте по выбранному набору, Graphify включайте всегда; для Orca предложите
нужные официальные Orca skills.

### 6. Итоговый план

До запроса применения самостоятельно подготовьте конкретный план: выбранные
совместимые версии и источники, известные отсутствующие инструменты/skills,
планируемые файлы/генераторы и команды проверок. Если версии нужно проверить
по сети, согласуйте такой просмотр в рамках диагностики.

Покажите короткое человеческое описание:

- Продукт и целевые приложения.
- Выбранный стартовый путь; для готовых требований — согласованное понимание и
  оставшиеся открытые вопросы, для технической подготовки — границы основы без
  придуманной функциональности продукта.
- Стек, локальная среда и способ запуска.
- Стандартный процесс требований, дизайна, реализации, проверки и ревью.
- Документы и конфигурация, которые появятся/будут дополнены в Git.
- Структурированная таблица проектных навыков: имя, назначение, репозиторий, ревизия,
  пути в `.agents/skills` и `.claude/skills`; отдельные списки агентов и референсов.
  Явно согласовать этот список перед установкой.
- Точные глобальные инструменты/источники для установки; уже установленные
  будут использованы. Обновления существующих навыков — отдельное решение.
- Опциональные компоненты и проверки готовности; известные ограничения.

Спросите один раз: «Применить этот план настройки?» Варианты: «Настроить»,
«Изменить выбор», «Отменить». Этот ответ разрешает только показанный объём.
Если пользователь заранее одобрил именно этот конкретный объём, достаточно
показать итог и продолжить. «Изменить» возвращает к затронутому вопросу.

## После опроса

Агент сам выполняет согласованный план: устанавливает стек по официальным
инструкциям, ставит недостающие навыки и копирует набор в `.agents/` и `.claude/`,
проводит [инициализацию репозитория](product-setup.md#инициализация-репозитория-продукта)
и завершает [чек-листом готовности](product-setup.md#критерии-готовности).
Пользователю показывает ход работы и итог: что готово, как запускать продукт,
какие проверки прошли. При блокере продолжает независимую работу, задаёт только
необходимый вопрос и не объявляет окружение полностью готовым.

Возобновление: читайте предыдущие ответы в чате и реестр набора продукта,
спрашивайте только изменившиеся/незаполненные параметры. Не запускайте опрос заново
для простого запроса проверки или обновления навыков.

Результат настройки включает отслеживаемые `.agents/`, `.claude/`, `MANUAL.md`,
`AGENTS.md`, `CLAUDE.md` и реестр `docs/agent-skills.md`. В инструкциях
на русском обязательны software-development-workflow и приоритет проектных навыков;
AGENTS.md/CLAUDE.md дополняют правилами на каждый запрос, маршрутизацией задач
по навыкам, контекстом продукта, конвенциями и командами проверки
(см. [product-setup.md](product-setup.md) и примеры итоговых файлов
[agents-md-example.md](agents-md-example.md),
[claude-md-example.md](claude-md-example.md)).
